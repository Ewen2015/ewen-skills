# 指标口径

一个改进项如果没有对应的指标，就先补度量，别先动手改——
否则永远分不清"变好了"和"我觉得变好了"。

所有指标都必须能从文件算出来。`scripts/rsi.py` 实现了标 ✅ 的那些。

## 闭环健康

| 指标 | 定义 | 怎么算 | 状态 |
| --- | --- | --- | --- |
| 闭环覆盖率 | 走到"发布"的书 / 全部书 | `rsi.py coverage` 的发布列 | ✅ |
| 断点数 | 每条链上"上一步有、下一步没有"的处数 | `rsi.py coverage` 的「断点」段 | ✅ |
| 孤儿产物 | 有成品但认不出是哪本书的目录数 | `rsi.py coverage` 的「孤儿产物」段 | ✅ |
| 端到端周期 | 读完 → 发布 的天数 | 卡片 `read_at` → 平台发布/排期时间 | ✅（近似） |
| 全周期 | 开始读 → 发布 | 需要记录"开始读"的时间戳 | ❌ 未埋点 |
| 用户介入次数 | 一次流程里需要用户亲自纠正/补做的处数 | 人工记一行：时间 + 哪一步 + 改了什么 | ❌ 未埋点（口径见 R20） |

## 供给侧（会不会断更）

| 指标 | 定义 | 现状 |
| --- | --- | --- |
| 选题缓冲 | 未用选题数 ÷ 每日发布数 | **0 天**（2 条全部已用） |
| 成品缓冲 | 已备好未发的成品数 | 2（已排到 2026-10-07） |
| 素材缓冲 | 已有笔记但没做成的书 | 0 |

**红线**：选题缓冲 < 7 天就是断更风险。这条比任何视觉优化都优先。

## 需求侧（有没有用）——必须按渠道分开算

**S4 是分支，不是节点。** 度量也要跟着分支走：每个渠道有自己的信号，
不能拿小红书的指标代表整条链（私域没有 reads，自用渠道没有赞，对话式取用没有收藏）。

先记账，再算比率。每个渠道至少要有"渠道名"和"取用计数"两个字段。

| 渠道 | 能拿到的信号 | 现在 |
| --- | --- | --- |
| 公开社交：小红书 | reads / likes / collects / shares | ✅ `state/state.json`（19 条） |
| 私域（朋友、群） | 回复、追问 | ❌ 无记录 |
| 自用（笔记、日记） | 是否回看 | ❌ 无记录 |
| 对话式（second-brain 回答） | recall 命中与采纳 | ❌ 未埋点 → R2 |
| 单页 / 打印版 | 是否读完、是否被再引用 | ❌ 无记录 |

小红书这一个渠道的指标（下面这些，只有它算得出来）：

| 指标 | 定义 | 怎么算 | 状态 |
| --- | --- | --- | --- |
| 阅读量 | 平台 reads | `state/state.json` 的 `history.published` | ✅ |
| 收藏率 | 收藏 ÷ 阅读 | 同上。**读书类内容看收藏率，不看点赞** | ✅ |
| 互动率 | (赞+藏+转) ÷ 阅读 | 同上 | ✅ |
| 关注转化 | 新增关注 ÷ 阅读 | 平台未抓，需补 | ❌ |

注意：单篇 reads 在几十的量级时，任何比率都是噪声。
样本 < 20 篇时只看趋势，别下结论；跨渠道比较时更要小心——口径根本不同。

## UI 侧（同一份内容，不同载体好不好读）

载体的好坏不靠感觉，靠可测的东西。随载体不同而不同：

| 载体 | 可测的量 |
| --- | --- |
| 图文卡片 | 字号下限、溢出、压页脚、孤字换行（`rednote-post` 已实测） |
| 单页 HTML | 三栏是否溢出、内容带 headroom（`scandinavian-style` 已实测） |
| 长文 | 分段长度、标题层级 |
| 对话 | 一次回答里被取用的卡片数、回答长度 |

这些是"**呈现**"维度的指标，和渠道指标正交——别混成一张表。

## 取用侧（北极星在这）

| 指标 | 定义 | 状态 |
| --- | --- | --- |
| **卡片取用率** | 被 recall 命中并实际读过的卡 ÷ 书库卡片数 | ❌ 未埋点 → R2 |
| 死卡数 | 从未被任何问题命中的卡 | ❌ 未埋点 → R2 |
| 落空率 | `recall` 返回全是弱匹配的次数 ÷ 总次数 | ❌ 未埋点 → R2 |
| 命中质量 | 采纳的候选排名（第 1 名命中率） | ❌ 未埋点 → R2 |

**北极星：卡片取用率。** 它直接对应这条流水线的目的。
它的反面（死卡数、落空率）同时告诉我们"书库里缺什么"——这是回流 B 的原料。

注意这里的"取用"是**跨所有出口**的：小红书被收藏、对话里被引用、单页被读完，
都算取用。现在的度量只覆盖了其中之一（小红书），所以北极星目前被低估。

## 成本侧

| 指标 | 定义 | 状态 |
| --- | --- | --- |
| 单本阅读耗时 | 从开始读到出笔记 | ❌ 未埋点（1 次手记，见下） |
| 单本发布耗时 | 笔记 → 成品 → 发布 | ❌ 未埋点（1 次手记，见下） |
| 找书耗时 | 决定读某本 → 拿到文件 | ❌ 未埋点（1 次手记，见下） |

这三项现在是空白。在补之前，任何"这样更快"的说法都没有依据。

### 样本 #1 · 2026-10-05《蓝海战略》（人工掐表，非埋点）

墙钟时间线，T0 = `11:29:41`（决定读这本、开始找书）：

| 阶段 | 时刻 | 用时 | 备注 |
| --- | --- | --- | --- |
| 检索候选 | 11:30:40 | 59s | 第一次 `search` 直接 argparse 报错（R29），修完才算数 |
| 候选短名单 → 用户确认 | 11:30:40 | ≈0 | 拿首轮候选问了用户 |
| 登录 + 下载 | 11:35:31 | ≈4m | 第一次 `download` 全挂（R30），补完登录、修完依赖才跑通 |
| **修 R29 + R30** | 12:02:32 | **27m01s** | 纯故障排查。**名义路径没有这一段** |
| 收编入库（`adopt`） | 12:02:32 | ≈0 | 一条命令 |
| 阅读 + 笔记 + 卡片 + 封面 | ≈12:11 | ≈8m30s | S2+S3 主体，含 5 张卡片渲染与实物书封 |
| 发布 | ≈12:21 | ≈10m | 含一次桥接超时**白等 5m**、标签行格式返工 |
| 收尾（state／归档／草稿清理／commit×2／push） | 12:28:45 | ≈8m | 这轮额外发现 R31/R32 |

- **端到端（T0 → 发布完成）≈ 51 分钟**；到"全部收尾"= **59 分 04 秒**。
- 其中 **≈32 分钟是故障与返工**（R29 + R30 27m、桥接超时 5m），不是这条流水线的正常成本。
- **名义路径估计 ≈ 15–16 分钟**（找书 ≈2m + 读/做图 ≈8.5m + 发布 ≈5m），但 n=1、且是估的，
  等下一个「无故障样本」再修正。

> 记法提醒：时间戳来自会话与文件 mtime，`12:11`／`12:21` 是区间推断，

## 记录纪律

- 每个数字标来源文件。`rsi.py` 的输出就是取证方式。
- 比率类指标必须同时给出样本量。
- 别把"新增了一个工具/脚本"当成指标——那是动作，不是结果。
