# 指标口径

一个改进项如果没有对应的指标，就先补度量，别先动手改——
否则永远分不清"变好了"和"我觉得变好了"。

所有指标都必须能从文件算出来。`scripts/rsi.py` 实现了标 ✅ 的那些。

## 闭环健康

| 指标 | 定义 | 怎么算 | 状态 |
| --- | --- | --- | --- |
| 闭环覆盖率 | 走到"发布"的书 / 全部书 | `rsi.py coverage` 的发布列 | ✅ |
| 断点数 | 每条链上"上一步有、下一步没有"的处数 | `rsi.py coverage` 的「断点」段 | ✅ |
| 孤儿产物 | 有成品但认不出是哪本书的目录数 | `rsi.py coverage` 的「孤儿产物」段 | ✅ |
| 端到端周期 | 读完 → 发布 的天数 | 卡片 `read_at` → 平台发布/排期时间 | ✅（近似） |
| 全周期 | 开始读 → 发布 | 需要记录"开始读"的时间戳 | ❌ 未埋点 |
| 用户介入次数 | 一次流程里需要用户亲自纠正/补做的处数 | 人工记一行：时间 + 哪一步 + 改了什么 | ❌ 未埋点（口径见 R20） |

## 供给侧（会不会断更）

| 指标 | 定义 | 现状 |
| --- | --- | --- |
| 选题缓冲 | 未用选题数 ÷ 每日发布数 | **0 天**（6 条全部已用）→ R1 |
| 成品缓冲 | 已备好未发的成品数 | 7（已排到 2026-10-11） |
| 素材缓冲 | 已有笔记但没做成的书 | 0（8 本书全部出过） |

**红线**：选题缓冲 < 7 天就是断更风险。这条比任何视觉优化都优先。

## 需求侧（有没有用）——必须按渠道分开算

**S4 是分支，不是节点。** 度量也要跟着分支走：每个渠道有自己的信号，
不能拿小红书的指标代表整条链（私域没有 reads，自用渠道没有赞，对话式取用没有收藏）。

先记账，再算比率。每个渠道至少要有"渠道名"和"取用计数"两个字段。

| 渠道 | 能拿到的信号 | 现在 |
| --- | --- | --- |
| 公开社交：小红书 | reads / likes / collects / shares | ✅ `state/state.json`（19 条） |
| 私域（朋友、群） | 回复、追问 | ❌ 无记录 |
| 自用（笔记、日记） | 是否回看 | ❌ 无记录 |
| 对话式（second-brain 回答） | recall 命中与采纳 | ❌ 未埋点 → R2 |
| 单页 / 打印版 | 是否读完、是否被再引用 | ❌ 无记录 |

小红书这一个渠道的指标（下面这些，只有它算得出来）：

| 指标 | 定义 | 怎么算 | 状态 |
| --- | --- | --- | --- |
| 阅读量 | 平台 reads | `state/state.json` 的 `history.published` | ✅ |
| 收藏率 | 收藏 ÷ 阅读 | 同上。**读书类内容看收藏率，不看点赞** | ✅ |
| 互动率 | (赞+藏+转) ÷ 阅读 | 同上 | ✅ |
| 关注转化 | 新增关注 ÷ 阅读 | 平台未抓，需补 | ❌ |

注意：单篇 reads 在几十的量级时，任何比率都是噪声。
样本 < 20 篇时只看趋势，别下结论；跨渠道比较时更要小心——口径根本不同。

## UI 侧（同一份内容，不同载体好不好读）

载体的好坏不靠感觉，靠可测的东西。随载体不同而不同：

| 载体 | 可测的量 |
| --- | --- |
| 图文卡片 | 字号下限、溢出、压页脚、孤字换行（`rednote-post` 已实测） |
| 单页 HTML | 三栏是否溢出、内容带 headroom（`scandinavian-style` 已实测） |
| 长文 | 分段长度、标题层级 |
| 对话 | 一次回答里被取用的卡片数、回答长度 |

这些是"**呈现**"维度的指标，和渠道指标正交——别混成一张表。

## 取用侧（北极星在这）

| 指标 | 定义 | 状态 |
| --- | --- | --- |
| **卡片取用率** | 被 recall 命中并实际读过的卡 ÷ 书库卡片数 | ❌ 未埋点 → R2 |
| 死卡数 | 从未被任何问题命中的卡 | ❌ 未埋点 → R2 |
| 落空率 | `recall` 返回全是弱匹配的次数 ÷ 总次数 | ❌ 未埋点 → R2 |
| 命中质量 | 采纳的候选排名（第 1 名命中率） | ❌ 未埋点 → R2 |

**北极星：卡片取用率。** 它直接对应这条流水线的目的。
它的反面（死卡数、落空率）同时告诉我们"书库里缺什么"——这是回流 B 的原料。

注意这里的"取用"是**跨所有出口**的：小红书被收藏、对话里被引用、单页被读完，
都算取用。现在的度量只覆盖了其中之一（小红书），所以北极星目前被低估。

## 成本侧

| 指标 | 定义 | 状态 |
| --- | --- | --- |
| 单本阅读耗时 | 从开始读到出笔记 | ❌ 未埋点（2 次手记，见下） |
| 单本发布耗时 | 笔记 → 成品 → 发布 | ❌ 未埋点（2 次手记，见下） |
| 找书耗时 | 决定读某本 → 拿到文件 | ❌ 未埋点（2 次手记，见下） |

这三项现在是空白。在补之前，任何"这样更快"的说法都没有依据。

  这是五个样本里第一次（前四个分别是 51m / 23m15s / 23m36s / 24m00s）。
- **R36 的 5 分钟没了。** `reset`+`fill`+`verify` 合计 ≈100s（5 张图 + 734 字正文 + 8 标签）。
  修复的根因见 backlog R36：**不是正文太长，是 `CMD_TIMEOUT` 在 server 进程启动时定死**，
  而端口上常驻着一个用旧默认起着的旧进程——调 CLI 侧的环境变量对它无效。
  调大默认值 + 让 `ensure_server` 发现旧进程就换掉，这个坑就没有了。
- **剩下的时间集中在一处**：封面（S1 的 4m13s）。R39 记了它是怎么解决的，
  以及为什么它现在**没有通路**——"电子封面"规则刚在 R33 放开，
  但刚好遇到一本内嵌封面只有 306×435 的书，规则名义上成立、实际不可用。

> **五个样本连起来看**：51m → 23m15s → 23m36s → 24m00s → **13m51s**。
> 前四个稳在 23–24 分钟，这一轮直接砍掉 ≈10 分钟，而且**砍掉的正好是前两轮
> 反复出血的那一处**。这印证了样本 #4 的结论：R36 是唯一"重复出现且仍需人工"的故障，
> 杠杆压在它身上是对的——一旦修掉，同一段工序从"跑满 5 分钟然后留一个半成品"
> 变成"100 秒干净跑完"。
>
> 但**故障率并没有同步归零，只是换了地方**：本轮新增 R38（交书入口的第三种形态）
> 和 R39（内嵌封面低于下限时没有通路），而 R39 一口气吃掉了本轮 **≈30%** 的端到端时间。
> 这仍然是那条主轴：**收敛的不是"故障率"，是"同一类故障不再重复"**。
> R35、R36 两个旧坑现在都能被机器自己跳出（R35 自愈、R36 代码级修复），
> 而每次腾出来的时间，都被一个新的、此前没有名字的工序吃掉。
>
> **下一步的杠杆**：把 R39 那种"模型临场判断"变成通路。封面回落的三步
> （内嵌封面 → 同书高清扫描件 → 报告给用户）现在全靠现场决定，第 ② 步最容易漏，
> 而它恰好是这轮最贵的一步。

**样本 #5 收尾后的更正（同日，用户纠错触发）**：上面"13m51s / 人工介入 0 次"成立，
但收尾时依据 `xhs_state.py` 报出的 🚩「10-07、10-08 两篇已排期笔记从平台消失」是**错的**——
用户确认两篇都还在队列里。真相是这条观测面在**静悄悄少报**：
Chrome 窗口不在前台 → 虚拟列表停发下一页请求 → 只读到首屏 10 张，
而脚本把这 10 张报成了 `scroll_exhausted: true`（详见 backlog **R40**）。

> 这一条不改时间数字，改的是**这次读数的可信度**：样本 #5 的端到端耗时依然是 13m51s，
> 但"排期缺口"这一类结论在本轮**全部作废**。也是同一个教训第一次以"度量"的面貌出现——
> 前面 R35／R36 都是**动作层**报错（报成功没落地／报失败做了一半），
> R40 是**观测层**报错（没读全却报读全了）。它比前两个更危险：
> 前两个至少会停，这个不会停，它会一路把错结论传到用户面前。
